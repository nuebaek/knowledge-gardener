## 📖 학습 내용

### Day 1 (06/15) — RAG 기본기

#### 1-1. RAG (Retrieval-Augmented Generation)

> 사용자 질문에 대해 외부 문서에서 관련 정보를 검색(Retrieval)하고, 이를 프롬프트에 보강(Augmented)해 LLM이 최종 답변을 생성(Generation)하는 아키텍처.

**핵심**
- **LLM의 3가지 한계를 극복**하기 위해 등장
  - **최신성 (Cut-off)**: 학습 이후 정보는 모름 → 외부 검색으로 실시간 정보 주입
  - **환각 (Hallucination)**: 없는 내용을 지어냄 → 근거 문서 기반 답변 강제
  - **내부/보안 데이터**: Fine-tuning 없이 사내 문서를 즉각 활용 가능
- 전체 흐름: 문서 로딩 → 청킹 → 임베딩 → VectorDB 저장 → 질문 임베딩 → 유사도 검색 → 프롬프트 증강 → 생성

**비유:** 사냥꾼이 쏜 사냥감을 물어오는 골든 리트리버처럼, 정보의 바다에서 질문에 딱 맞는 문서를 물어와 LLM에 전달하는 역할(Retriever)

---

#### 1-2. Tokenization

> 자연어 문장을 컴퓨터가 이해할 수 있는 최소 단위(토큰)로 쪼개는 과정. 현대 트랜스포머 모델은 서브워드(Sub-word) 방식을 기본으로 사용.

**핵심**
- 단어 단위 분리의 한계: 사전에 없는 합성어(OOV) 처리 불가
- 서브워드(Sub-word) 토큰화: 단어를 더 작은 의미 단위로 쪼개 어휘 사전에 매핑 → OOV 문제 해결
- 컨텍스트 윈도우(Context Window): 모델이 한 번에 처리할 수 있는 최대 입력 크기(토큰 단위). "100만 글자"가 아니라 "100만 토큰"

---

#### 1-3. Text Embedding

> 토큰화된 텍스트를 다차원 실수 벡터로 변환하는 과정. 단어/문장의 '의미'를 벡터 공간의 좌표값으로 표현.

**핵심**
- 의미적으로 유사한 단어/문장은 벡터 공간에서 가까이 위치
- RAG의 핵심 역할: 문서 청크와 사용자 질문을 **같은 벡터 공간**으로 변환해 유사도 비교 가능하게 만듦

---

#### 1-4. Dense Vector / Sparse Vector

> 텍스트를 벡터로 표현하는 두 가지 방식.

**핵심**

| 구분 | Sparse Vector | Dense Vector |
|---|---|---|
| 차원 | 어휘 사전 크기 (수만 차원) | 압축된 저차원 (수백 차원) |
| 값 | 대부분 0 | 모두 실수 |
| 특성 | 키워드 정확 일치 강점 | 의미 유사도 검색 강점 |

- 스파스 벡터: 원-핫 인코딩 방식, 해당 단어 위치만 1
- 밀집 벡터: 희소 벡터를 저차원으로 압축, 단어 간 의미적 관계를 내포 — RAG에서 사용하는 방식

---

#### 1-5. Sentence Transformers

> 단어가 아닌 문장 전체를 하나의 밀집 벡터로 변환하는 오픈소스 임베딩 모델.

**핵심**
- 목적이 생성이 아닌 의미 파악 → 트랜스포머 중 **인코더(Encoder) 계열** 모델을 사용하는 것이 유리
- GPT처럼 다음 단어를 '생성'하는 디코더와 달리, BERT 같은 인코더는 문장 전체를 읽고 의미를 이해하는 데 특화

---

#### 1-6. VectorDB

> RAG 파이프라인에서 임베딩 결과물(밀집 벡터), 메타데이터, 원본 텍스트를 저장하고 고속 유사도 검색을 수행하는 AI 전용 데이터베이스.

**핵심**
- 기존 RDB와의 차이: RDB는 정형 테이블+SQL 문법 검색이라 의미 기반 검색 불가, VectorDB는 네이티브 시맨틱 검색 지원
- "AI의 해마(Hippocampus)" — 없으면 LLM은 매번 기억상실증에 걸린 것처럼 맥락 유지 불가
- 컬렉션(Collection) 단위로 데이터 관리 (NoSQL에서 차용, RDB의 Table에 해당)

**6-1. HNSW (Hierarchical Navigable Small World)**
- VectorDB에 특화된 계층형 인덱싱 알고리즘. 풀 스캔 없이 고속 유사도 검색을 가능하게 함
- 벡터들을 클러스터링해 대표 벡터들로 최상위 레이어 구성 → 대표 벡터와 먼저 비교 → 범위 좁히며 하위 레이어로 점진적 탐색

**6-2. ChromaDB**
- 원본 텍스트+메타데이터+벡터를 함께 저장·관리할 수 있는 현대적 VectorDB. 기본 HNSW 인덱싱 내장

**6-3. FAISS**
- 페이스북에서 만든 1세대 벡터 DB. GPU 가속 지원하지만 벡터만 저장(원본 텍스트·메타데이터 별도 관리 필요)해 현재는 ChromaDB에 밀림

---

#### 1-7. Chunking

> 방대한 문서를 LLM 컨텍스트 윈도우 한계와 검색 정확도를 위해 작은 덩어리(Chunk)로 나누는 전처리 과정.

**핵심**
- 오버랩(Overlap): 이전 청크 끝 일부를 다음 청크 시작에 겹치게 → 청크 경계 문맥 단절 방지

**7-1. Regex & Delimiter Chunking**: 마침표·줄바꿈·마크다운 헤딩 등 구분자 기준 분할, 또는 정규표현식으로 특정 패턴(법률 조항 등) 정확히 분리

**7-2. Semantic Chunking**: 인접 문장들 간 코사인 유사도를 기준으로 주제가 바뀌는 지점에서 분할. 장점: 의미 단위로 완벽히 묶여 검색 품질 매우 높음 / 단점: 문장마다 임베딩 연산 필요해 속도가 극악으로 느림

**7-3. Parent-child Chunking**: 부모(2,000자)·자식(500자) 청크로 계층 분할. VectorDB에는 자식 청크만 임베딩하고, 검색은 자식으로 정밀하게, LLM 프롬프트에는 부모 청크 원본 전달 — 검색은 좁고 날카롭게 + 모델에는 풍부한 맥락 제공

---

#### 1-8. RAG 파이프라인 구현 흐름

1. **문서 로딩**: 매뉴얼, FAQ 등 비정형 자연어 문서 로드
2. **청킹**: 컨텍스트 윈도우 한계에 맞게 분할 + 오버랩 적용
3. **인덱싱 & 저장**: 청크 → 임베딩 → 벡터 변환 → VectorDB 저장
4. **유사도 검색**: 질문도 동일 임베딩 모델로 벡터화 → 코사인 유사도 계산 → Top-K 추출
5. **프롬프트 증강 & 생성**: **벡터가 아닌 원본 텍스트**로 결합해 LLM에 전달

> [!NOTE] 왜 벡터가 아닌 텍스트로 전달하나?
> 리트리버의 임베딩 공간과 LLM 내부의 임베딩 공간이 서로 다르기 때문. LLM은 전달받은 원본 텍스트를 자신의 토크나이저로 새롭게 재변환하므로 공간 충돌이 발생하지 않음.

### Day 2 (06/16) — RAG 검색 고도화

#### 2-1. 파라메트릭 지식의 한계와 RAG의 본질

> **파라메트릭 지식**: LLM이 학습을 통해 가중치 안에 압축 저장한 지식. **논파라메트릭 지식**: 외부 DB·문서에 존재하는 지식. **RAG**: LLM의 파라메트릭 지식 한계를 외부 논파라메트릭 지식으로 보완하는 아키텍처.

**핵심**
- LLM 자체 지식은 용량 한계가 있고, 잘못 학습된 가중치로 인한 할루시네이션이 발생 가능
- 기본 파이프라인: 사용자 질문 → 임베딩 → VectorDB Top-K 검색 → 질문+검색 문서를 LLM에 프롬프트로 전달 → 최종 응답

**비유:** 인간도 장기 기억력 한계로 책·인터넷·노션을 찾아봄. RAG는 AI가 자신의 뇌(LLM) 한계를 외부 노트(Vector DB)로 보완하게 만드는 것.

---

#### 2-2. FastAPI + ngrok 서빙 & API 보안

**핵심**
- **ngrok**: Colab 내부의 localhost를 퍼블릭 도메인으로 터널링. 외부 서빙에 필수
- **nest_asyncio**: Colab 내에서 비동기 루프가 돌아가도록 설정하는 모듈
- ⚠️ API 키 하드코딩 절대 금지 — Colab Secrets 메뉴에 저장 후 `userdata.get('키이름')`으로 불러오기
- Colab vs 로컬 개발 분리: 개발·디버깅은 로컬(VS Code), GPU 서빙 테스트는 최종에만 Colab

---

#### 2-3. 하이브리드 검색 (Hybrid Search)

> 의미 기반 **덴스(Dense) 검색**과 키워드 기반 **스파스(Sparse) 검색**을 동시에 수행하고, 두 점수를 가중 합산해 최종 Top-K를 결정하는 기법.

**핵심**

| | 덴스(Dense) 검색 | 스파스(Sparse) 검색 |
|--|--|--|
| 기반 | 임베딩 벡터 + 코사인 유사도 | TF-IDF / BM25 (단어 빈도) |
| 강점 | 의미 유추 (자동차 ≈ 차량) | 정확한 키워드 매칭 |
| 약점 | 고유명사·정확한 키워드에 약함 | 의미 유추 불가 |

- 두 방식은 서로의 단점을 보완하는 거울 관계 → 앙상블로 검색 품질 극대화

**비유:** 하이브리드 자동차가 상황에 따라 내연기관과 전기 모터를 섞어 쓰는 것

---

#### 2-4. 쿼리 확장 (Query Expansion)

> 사용자 질문을 그대로 검색하지 않고, LLM으로 질문을 더 구체적으로 재구성하거나 관련 용어를 추가해 검색 범위를 넓히는 기법.

**핵심**
- 트레이드오프: 빠른 구현 가능하지만 LLM 추가 호출 → 속도↓ 비용↑, 지시를 100% 완수 못할 수 있음, 디버깅 어려움(블랙박스)

> [!NOTE] 코드 규칙 → 프롬프트로의 진화
> 과거엔 오타 수정, 사용자 의도 탐지, 가드레일 필터링을 규칙 기반 코드로 구현했음. 이제는 LLM에게 자연어 명령으로 위임하는 추세.

---

#### 2-5. 리랭킹 (Re-ranking)

> 1차 검색으로 빠르게 확보한 후보 문서들을, 별도의 정밀 모델로 질문과의 관련성을 다시 평가해 순위를 재정렬하는 기법.

**핵심 — 바이 인코더 vs 크로스 인코더**

| | 바이 인코더(Bi-encoder) | 크로스 인코더(Cross-encoder) |
|--|--|--|
| 방식 | 질문·문서를 따로 임베딩 후 유사도 계산 | 질문+문서를 하나의 쌍으로 합쳐 입력 |
| 속도 | 빠름 | 느림 |
| 정확도 | 상대적으로 낮음 | 높음 |
| 사용 단계 | 1차 후보 추출(전체 문서) | 2차 정밀 재순위(1차 후보에만) |

**비유:** 프랑스 결선 투표. 예선 2등이 결선 1등이 될 수 있듯, 1차 검색 순위가 항상 최선이 아님.

---

#### 2-6. HyDE (Hypothetical Document Embeddings)

> 사용자 질문을 바로 임베딩하지 않고, LLM에게 "이 질문의 가상 답변 문서"를 먼저 생성시킨 뒤, 그 가상 답변으로 실제 문서를 검색하는 기법.

**핵심**
- 사용자 질문은 "의문문", DB 문서는 "평서문" 형태라 결이 달라 직접 비교 시 매칭이 잘 안 됨
- 가상 답변(평서문)을 만들면 DB 문서와 결이 맞아 검색 품질↑
- ⚠️ LLM 추가 호출로 속도↓ 비용↑

---

#### 2-7. 대화형 RAG (Conversational RAG / 멀티턴)

> 이전 대화 기록(Chat History)을 고려해 문맥을 이어가는 멀티턴 RAG 시스템.

**핵심**
- LLM은 기본적으로 **무상태(Stateless)** — 이전 대화를 스스로 기억 못함. 시스템이 명시적으로 히스토리를 넘겨줘야 함
- 턴마다 [유저 질문-LLM 답변] 쌍을 히스토리 메모리에 저장

**컨텍스트 윈도우 한계 돌파 전략**

| 전략 | 방식 |
|------|------|
| 트리밍(Trimming) | 최근 N개의 대화만 잘라서 남김 |
| 요약(Summarization) | 이전 대화 전체를 LLM이 짧게 요약해 맥락으로 주입 |

### Day 3 (06/17) — 컨텍스트 엔지니어링과 평가

#### 3-1. 프롬프트 엔지니어링 vs 컨텍스트 엔지니어링

> **프롬프트 엔지니어링**: 생성형 AI로부터 원하는 출력을 만들기 위해 자연어 입력을 구조화하는 과정. **컨텍스트 엔지니어링**: 프롬프트 엔지니어링의 상위 개념. "사용자 입력이 아닌 것들"(시스템 지침, 메타데이터, API 툴 등)과 "프롬프트의 맥락"을 관리·결합하는 기술.

**핵심**
- 핵심은 **초개인화(Hyper-personalization)** — 각자에게 딱 맞는 콘텐츠를 원하는 형식으로 제공
- 개발자는 사용자 질문 + 백그라운드 정보를 코드 레벨에서 자동 조립해 LLM에 전달

| | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|--|--|--|
| 초점 | 사용자의 자연어 입력 구조화 | 프롬프트 외 모든 맥락 정보 관리 |
| 예시 | "3줄 요약해줘" | 시스템 지침, RAG 검색 결과, API 툴 정보 |

---

#### 3-2. In-Context Learning (컨텍스트 내 학습)

> AI 모델이 가중치(파라미터)의 영구적 변화 없이, 프롬프트로 제공된 맥락 정보만으로 임시적으로 지식을 습득하고 답변하는 능력.

**핵심**
- RAG에서 문서를 넣거나 검색해도 **LLM 자체의 가중치는 1%도 변하지 않는다** — 매번 프롬프트로 먹이는 것
- 한계: 매번 프롬프트에 정답 맥락을 포함해야 하는 비효율적 우회로

**비유:** 졸업 후 취업한 사람에게 새 업무 매뉴얼을 그때그때 쥐여주는 것. 뇌(가중치)가 변하는 게 아니라 읽고 참고해서 답하는 것.

---

#### 3-3. 스파스 검색 — BOW & TF-IDF

**3.1 BOW (Bag of Words)**: 단어 등장 횟수만 세서 문서를 표현. "관사, 조사" 같은 흔한 단어의 점수가 과도하게 높아지는 단점

**3.2 TF-IDF**: BOW의 한계를 보완, 특정 문서에서 자주 나왔지만 전체 문서에서는 드문 단어를 중요하게 봄
- TF(Term Frequency): 해당 문서에서 단어가 나온 횟수
- IDF(Inverse Document Frequency): 전체 문서 중 그 단어가 등장한 문서 수의 역수에 log — 흔한 단어는 IDF 낮음, 희귀 키워드는 IDF 높음
- TF-IDF = TF × IDF

---

#### 3-4. 질문 재구성 (Query Rewriting) & 오케스트레이션

**핵심**
- 멀티턴 대화에서 "그게 뭐야?" 같은 대명사/불명확한 표현을 LLM이 완전한 독립 질문으로 재구성 → 벡터 DB 검색
- **오케스트레이션**: 최종 응답 생성뿐 아니라 중간 과정(질문 재구성, 라우팅 등)에서도 LLM을 적극 호출하는 연쇄 구조. 질문 하나에 LLM 호출이 5개 이상 연쇄 발생 가능 → 비용·속도 트레이드오프 → 스트리밍 UX로 체감 속도 보완

---

#### 3-5. RAG 평가 지표

> RAG 파이프라인의 성능 병목을 찾기 위해, **검색(Retrieval)**과 **생성(Generation)**을 분리해서 정량 평가.

**핵심 — 4대 평가 지표**

| 분류 | 지표 | 무엇을 측정 |
|------|------|------------|
| 검색 | Context Precision | 뽑아온 문서 중 노이즈(무관한 문서)가 얼마나 적은가 |
| 검색 | Context Recall | 반드시 필요한 핵심 문서를 누락 없이 모두 찾았는가 |
| 생성 | Faithfulness | LLM이 검색된 문서에 근거해서 답했는가(환각 여부) |
| 생성 | Answer Relevance | 최종 답변이 원래 질문의 의도와 얼마나 일치하는가 |

- 정량 지표로 소통: "답변이 나아졌어요"(❌) 대신 "Faithfulness가 0.65 → 0.85로 올랐어요"(✅)
- 정답셋(Ground Truth) 구축은 사람이 직접 만들어야 하는 고된 작업

---

#### 3-6. LLM-as-a-Judge

> 수많은 응답 결과를 사람이 일일이 채점하는 대신, 최고 성능 LLM에게 채점 프롬프트를 주어 자동 판정하게 하는 평가 기법.

**핵심**
- 평가용 LLM에게 `질문 + 검색된 맥락 + 생성된 답변`을 넘기고 0~1점 채점 + **이유도 함께**(CoT 강제)
- 전략: 일반 서비스용은 저렴한 모델, 평가·채점용은 프론티어 모델을 짧게 사용

```
[월 06/15] RAG 기본기
    RAG(왜 필요한가) → Tokenization → Text Embedding(Dense/Sparse)
    → Sentence Transformers → VectorDB(HNSW/ChromaDB/FAISS) → Chunking(Delimiter/Semantic/Parent-child)
    ↓ (기본 파이프라인은 됐는데, 검색 품질을 더 끌어올리려면?)
[화 06/16] RAG 검색 고도화
    파라메트릭/논파라메트릭 지식 구분 → 하이브리드 검색(Dense+Sparse)
    → 쿼리 확장 → 리랭킹(Bi/Cross-encoder) → HyDE → 멀티턴(Trimming/Summarization)
    ↓ (검색이 좋아져도, LLM에게 "어떻게" 입력을 줄지 + 잘 됐는지 확인은?)
[수 06/17] 컨텍스트 엔지니어링과 평가
    프롬프트 → 컨텍스트 엔지니어링 → In-Context Learning(가중치 불변)
    → BOW/TF-IDF(스파스 검색 기반) → 질문 재구성/오케스트레이션
    → RAG 평가(Precision/Recall/Faithfulness/Relevance) → LLM-as-a-Judge
```

이번 주는 RAG를 "왜 필요한가"에서 시작해 "기본 파이프라인을 어떻게 짜는가", "검색 품질을 어떻게 더 끌어올리는가", 마지막으로 "그 결과를 어떻게 정량적으로 확인하는가"까지 하나의 완결된 사이클로 이어졌다. 월요일에 배운 토큰화·임베딩·VectorDB·청킹은 화요일 하이브리드 검색·쿼리 확장·리랭킹·HyDE의 재료가 되고, 수요일의 컨텍스트 엔지니어링과 RAG 평가는 그 전체 파이프라인을 "잘 설계했는지"와 "실제로 잘 작동하는지"를 검증하는 상위 관점이었다. 특히 화요일의 오케스트레이션(LLM 다중 호출)과 수요일의 In-Context Learning(가중치는 안 변한다)이 만나는 지점에서, RAG는 결국 "모델을 바꾸는 게 아니라 모델에게 매번 좋은 입력을 만들어주는 시스템"이라는 게 이번 주 전체를 관통하는 결론이었다.
