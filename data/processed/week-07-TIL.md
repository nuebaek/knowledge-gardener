## 📖 학습 내용

### Day 1 (06/22) — LangChain 기초

#### 1-1. LangChain

> 바닐라 RAG = 순정 파이썬으로 직접 짠 RAG / 랭체인 = AI 앱 부품을 표준 인터페이스로 엮어주는 프레임워크.

**핵심**
- 프롬프트, 모델, 출력 파서, 검색, 메모리 등 컴포넌트를 표준화된 인터페이스로 제공하는 프레임워크
- 반복적으로 필요한 LLM 기능을 표준화된 컴포넌트로 조립해서(부품화) 개발 속도를 높이고 유지보수 비용을 줄이면서, 실무에서 변경·확장이 쉬운 구조를 만들 수 있어 사용
- 컴포넌트(부품) → 인터페이스(통신 약속) 표준화 → 파이프라인으로 연결

**비유:** 프레임워크 = "용의 역린". 편하고 표준 정답을 주지만, 랭체인이 지원 안 하는 커스텀 요구가 들어오면 쌓아올린 구조가 무너져 개발자가 분노 → 유연성을 앗아간다는 본질적 한계.

---

#### 1-2. Prompt Templates

> 자연어 명령 안에 실행 시점에 값이 꽂힐 변수 구멍(`{}`, Placeholder)을 뚫어둔 컴포넌트.

**핵심**
- **PromptTemplate**: 문자열에 변수 구멍 → 딕셔너리(또는 키워드 인자)로 주입(`invoke`/`format`) → 완성 문자열
  - `invoke()`: 딕셔너리 형태로 값을 받음, 프롬프트 객체 반환 / `format()`: 키워드 인자로 값을 받음, 완성된 문자열만 반환
- **ChatPromptTemplate**: 역할(System/Human/AI)을 메시지 객체 단위로 구조화. 모델마다 역할 주입 방식이 다른데 랭체인이 알아서 최적화
  - `system`: 모델 행동 방식·규칙 / `human/user`: 사용자 질문·요청 / `ai/assistant`: 모델의 이전 응답(대화 히스토리용)
- **FewShotPromptTemplate**: 지시문 뒤에 입출력 예시 몇 개를 미리 주입해 응답 형식·패턴을 유도
  - zero-shot(예시 없이 지시만) vs few-shot(2~5개 예시로 패턴 파악)
- **MessagesPlaceholder**: 대화 이력처럼 개수가 변하는 메시지 리스트가 통째로 들어갈 자리를 미리 확보하는 특수 플레이스홀더

**비유:** 로그인 칸의 회색 안내문(주민번호 형식)이 일상 속 플레이스홀더. FewShot 예시 끝을 명사형으로 처리하면 LLM 실제 답변도 명사형으로 딱 떨어지게 포맷 일치.

---

#### 1-3. Structured Output

> LLM의 비정형 자연어 응답을, 코드에서 바로 다룰 수 있는 JSON, 클래스 객체 같은 정형 데이터로 변환하는 기술.

**왜 쓰는가**
- 과거 RDB는 데이터가 이미 정형. 지금은 자연어로 묻고 자연어로 받음 → 비즈니스 로직(백엔드)에 태우려면 자연어 → 정형 변환이 필수

**핵심 3가지 방식**

| 방식 | 언제 | 반환물 |
|---|---|---|
| `with_structured_output()` | 프론티어 모델(Gemini, GPT-4 등) | 모델 레벨에서 Pydantic 스키마 인지 → 완벽한 구조화 객체 |
| `JsonOutputParser` | 구조화 미지원 저렴/오픈소스 모델 | `format_instructions`로 JSON 강제 → dict |
| `PydanticOutputParser` | 위와 동일 원리 + 검증 필요 | 타입 검증(Validation) 포함 Pydantic 인스턴스 |

- `with_structured_output()`을 지원하는 모델 사용 시 대부분 이게 가장 안정적 → 실무 우선 선택
- Pydantic 스키마로 강제 정형화 = **RAG 백엔드 연동의 알파이자 오메가**

---

#### 1-4. LCEL과 Runnable 인터페이스

> LCEL = 컴포넌트를 파이프(`|`)로 선언적으로 잇는 문법. Runnable = 모든 컴포넌트가 공통 상속하는 표준 실행 규칙.

**핵심**
- `chain = prompt | model | parser` → 프롬프트 출력이 모델로, 모델 출력이 파서로 흐름
- Runnable이라 종류가 달라도 동일 메서드로 실행: `invoke`(단일) / `batch`(다중) / `stream`(실시간) (+ `ainvoke` 비동기)

**Core 3종**
- **RunnablePassthrough**: 입력을 변형 없이 통과 or 기존 입력에 새 키를 얹어 전달 — 맥북 USB 허브가 전원을 그대로 패스스루하는 것
- **RunnableParallel**: 여러 Runnable을 동시 실행 → 각 출력을 키에 매핑해 하나의 dict로 합침 — 건전지 병렬 연결처럼. 랭그래프 분기 처리의 기초
- **RunnableBranch**: `if/elif/else`처럼 입력 조건에 따라 실행 경로(체인)를 분기

**비유:** 파이프라인 `prompt | model | parser`는 본질이 수학의 함수 합성($h \circ g \circ f$). 프레임워크 유행은 사라져도 수학적 본질은 영원 → 코드를 늘 함수·연산 관계로 치환해 보는 습관.

---

#### 1-5. 대화 이력(History) 관리와 멀티 유저 세션

> `RunnableWithMessageHistory`로 과거 대화 문맥을 저장하고 다음 프롬프트에 자동 주입하는 기능.

**왜 쓰는가**
- LLM은 기억이 없음. 우리 서비스는 멀티 유저 시스템 — 모든 사용자 기록을 한 메모리에 섞으면 영화 *허(Her)*처럼 AI가 수백 명과 동시에 사랑에 빠지는 맥락 붕괴 → 유저별/기기별 세션 ID 발급, 이력 격리 보관

**핵심 — 트리밍(Trimming)**
- 대화가 길어지면 컨텍스트 윈도우 한계 초과 → 과거 이력을 잘라내야 함
- 방식: 최근 N턴만 남기기 또는 토큰 개수 기준으로 오래된 이력 잘라내기
- **System 메시지는 항상 보존**(지시가 사라지면 안 되니까), 그 외 메시지만 최근 것 위주로 잘라낸다

**비유:** 책상이 좁으면(컨텍스트 윈도우), 꼭 필요한 업무 지침서(System)는 항상 펼쳐두고 옛날 메모지(오래된 턴)는 치워서 자리를 확보.

---

#### 1-6. 다큐먼트 로더(Document Loaders)와 스크래핑 실무

> 텍스트·PDF·웹·폴더 등 외부 데이터를 읽어 랭체인 규격 `Document` 객체(본문 + 메타데이터) 리스트로 표준화하는 컴포넌트.

**로더 4종**
- **TextLoader**: 텍스트 파일 로드, 큰 파일은 `lazy_load`로 필요할 때 페이지 단위로
- **PyPDFLoader**: 복잡한 PDF를 페이지 단위로 쪼개 로딩
- **WebBaseLoader**: URL → BeautifulSoup로 HTML에서 본문만 스크래핑
- **DirectoryLoader**: 폴더 내 다수 파일을 와일드카드(`*.txt`, `**/*.md`)로 일괄 로딩

**비유:** 스크래핑의 고충 — 상세페이지가 통 이미지 1장이면 스크래핑 불가 → 비싼 OCR API 필요. HTML 구조·디자인 태그가 수시로 바뀌어 크롤러가 자주 깨짐.

### Day 2 (06/23) — RAG 파이프라인 추상화

#### 2-1. 다중 모델 오케스트레이션 (Multi-model Orchestration)

> 단일 LLM에 의존하지 않고 여러 모델을 지휘·조합해 단일 프론티어 모델을 능가하는 설계 기법.

**왜 쓰는가**
비용과 성능의 균형. 쉬운 작업은 로컬 오픈 모델, 어려운 작업만 유료 클라우드 모델로 라우팅해서 토큰/비용을 아낀다.

**핵심**
- **전처리 라우팅**: 입구에 사령탑(Coordinator) 모델이 작업을 분석 → 가장 적합한 모델 하나를 **선택해 위임**
- **후처리 퓨전 (Model Fusion)**: 모든 모델에 **병렬로 다 시킨 뒤**, 재판관(Aggregation) 모델이 결과를 종합
- 로컬 오픈 모델은 아직 툴 콜링(함수 호출) 능력이 약해 무한 루프에 빠지는 등 한계가 있다

**비유:** 라우팅 = 한 명의 전문가에게 일감 배정하는 팀장 / 퓨전 = 여러 명에게 다 시키고 결과를 모아 결정하는 합의체.

---

#### 2-2. 텍스트 스플리터 (Text Splitter)와 청킹

> 컨텍스트 한계를 넘기 위해 긴 문서를 작은 청크 리스트로 나누는 랭체인 표준 인터페이스.

**핵심**
- **CharacterTextSplitter**: 단일 구분자(예: `\n\n`) 기준 + 청크 사이즈/오버랩 설정
- **RecursiveCharacterTextSplitter**: 구분자 리스트를 우선순위대로 시도(`\n\n` → `\n` → 공백 → 글자). 잘랐는데도 사이즈 초과면 그 덩어리 안에서 다음 구분자를 재귀적으로 적용 → 의미 단절 최소화
- **TokenTextSplitter**: `tiktoken` 등 토크나이저 기반 토큰 수로 강하게 절단

**비유:** Recursive = 큰 가위로 자르고, 너무 크면 작은 가위로 또 자르는 식. Token = 효율적이지만 글자가 깨져 보임.

---

#### 2-3. 임베딩(Embedding)의 본질

> 자연어를 다차원 실수 벡터(예: 3072차원)로 투영하는 것. 단, 두 종류를 혼동하면 안 됨.

**핵심**
- **트랜스포머 내부 토큰 임베딩**: 모델 아키텍처의 부품. 다음 단어 예측을 위해 역전파로 가중치가 학습되는 파라미터. 유사도 검색용이 아님
- **검색용 임베딩 (Word2Vec 계열)**: 구글 Word2Vec 논문 기원. "문서를 벡터로 만들어 의미 기반 유사도 검색"이라는 단일 목적으로 분리·발전한 기술. **RAG에서 쓰는 게 이것**

**비유:** 같은 "임베딩"이라는 단어를 쓰지만 태생과 목적이 완전히 다른 두 기술.

---

#### 2-4. 벡터 스토어(Vector Store) 추상화 인터페이스

> Chroma, FAISS, Pinecone, Qdrant 등 여러 벡터 DB를 동일 문법(`similarity_search` 등)으로 다루게 묶은 공통 인터페이스.

**왜 쓰는가**
DB 바꿀 때마다 고유 SDK/API를 새로 배우고 코드를 뒤엎으면 유지보수 불가. 추상화하면 연결 객체만 갈아끼우고 나머지 로직은 재사용

**핵심**
- **JDBC 비유**: 자바가 수많은 RDB를 통합하려고 JDBC를 만든 것과 같은 원리(인터페이스의 다형성)
- 면접 팁: 화려한 AI 기술보다 인터페이스/다형성 같은 SW 공학 펀더멘털이 면접관을 사로잡는다

**비유:** 콘센트 규격(어댑터) — 뒤에 어떤 발전소든 플러그만 맞으면 그대로 쓴다.

---

#### 2-5. 리트리버(Retriever)와 고급 검색 기법

> 벡터 스토어에서 '검색' 기능만 떼어내, LCEL 체인(`prompt | model | parser`)에 런너블 부품으로 끼우는 인터페이스.

**핵심 (고급 검색 기법)**
- **앙상블 + RRF**: Dense(의미) + Sparse(키워드) 결과를 결합. RRF는 기준이 다른 점수 대신 **등수(rank)를 역수 취해 합산**: `Score = 1/(k+rank1) + 1/(k+rank2)`
- **MultiQuery(쿼리 확장)**: 단일 쿼리를 LLM이 여러 관점 쿼리로 변형·확장 후 다중 검색
- **Contextual Compression**: 검색된 문서에서 핵심만 필터·압축해 토큰 절약
- **Parent Document**: 검색은 작은 자식 청크로 정밀하게, LLM엔 문맥 풍부한 부모 청크 원본을 전달

### Day 3 (06/24) — LangSmith

> 이 날짜는 정식 배움일지 없이 짧은 노트(`26-06-24.md`)만 남아 있다. 위클리 챌린지 실습 위주의 하루였던 것으로 보이며, 노트에 남은 내용은 LangSmith 도구 소개와 새 프로젝트 셋업 명령뿐이라 아래 항목 하나로 정리한다.

#### 3-1. LangSmith

> LLM 애플리케이션을 만들고 나면, 그 실행 과정을 추적(Trace)하고 응답 품질을 평가하며 프롬프트를 버전 관리할 수 있게 해주는 LangChain 진영의 관측·평가 플랫폼.

**핵심**
- LCEL 체인이나 LangGraph처럼 여러 컴포넌트가 연쇄 호출되는 구조에서는, 어디서 얼마나 시간이 걸리고 어떤 입출력이 오갔는지 로그로 남기기 어렵다 — LangSmith가 이 실행 흐름을 자동으로 추적해 대시보드로 보여준다
- 프로젝트 셋업은 `uv init`으로 가상환경을 만들고 `uv add dotenv` 등으로 의존성을 추가하는 방식(uv 기반 프로젝트 관리)

```
    → Retriever + 고급 검색(RRF/MultiQuery)
    ↓ (조립한 파이프라인이 실제로 잘 도는지 어떻게 보나?)
[수 06/24] LangSmith
    LCEL/LangGraph 실행 흐름 추적·평가·프롬프트 버전 관리
```

이번 주는 "랭체인은 새 마법이 아니라 부품 + 표준 인터페이스 + 파이프 합성"이라는 월요일의 결론이 화요일까지 그대로 이어진 주였다. 월요일에 배운 프롬프트 템플릿·구조화 출력·LCEL·문서 로더가 각각의 "부품"이었다면, 화요일은 그 부품들 중 RAG에 특화된 것들(스플리터·임베딩·벡터스토어·리트리버)을 "추상화"라는 하나의 키워드로 다시 묶었다. 특히 벡터 스토어 추상화를 JDBC에 빗댄 비유와, LCEL 파이프를 함수 합성($h \circ g \circ f$)으로 본 관점이 이번 주를 관통한다 — 프레임워크의 구체적인 문법은 바뀌어도, "인터페이스로 구현을 감추고 부품처럼 갈아끼운다"는 소프트웨어 공학의 본질은 변하지 않는다는 것. 수요일의 LangSmith는 그렇게 조립한 파이프라인을 "눈으로 확인하는" 도구라는 점에서, 부품 조립의 다음 단계로 자연스럽게 이어진다.
