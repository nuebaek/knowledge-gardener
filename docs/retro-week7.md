# 7주차 회고

> 기술 스택, 아키텍처, 평가 수치는 [README](../README.md) 참고.

## 어려웠던 점

**검색 실패 디버깅**

"이미지 분류의 주요 과제는 무엇인가?" 질문에 모델이 계속 "자료에서 찾을 수 없다"고 답했다. 처음엔 `k`(검색 문서 수) 문제라 생각해 늘려봤지만 해결되지 않았다. 청크를 직접 확인해보니 원인은 두 가지였다 — 문서에 "Challenges" 섹션이 있었지만 헤더로 분리되지 못한 것, 그리고 긴 섹션이 길이 기준으로 재분할되면서 뒤쪽 청크는 어떤 섹션인지 맥락이 사라진 것. 헤더 경로를 서브청크 앞에 다시 주입하는 `_inject_header_context`를 만들어 상위 맥락을 포함시켜 해결했다.

**API 설계**

FastAPI로 래핑하면서 어려웠던 점과 해결 방식은 다음과 같다:

- **`lifespan`에서 체인 1회 구성:** 서버 시작 시 `build_rag_chain()`을 한 번만 호출해 `app.state.rag`에 보관. 요청마다 인덱싱을 반복하지 않는다.
- **`build_rag_chain()` 캡슐화:** 평가 스크립트(`baseline.py`)와 API 서버가 같은 체인을 쓰게 했다. 평가와 서빙이 다른 로직이면 점수가 실제 품질을 보장하지 못한다.
- **레이어 분리:** `routers/ask.py`(입력 검증) → `controllers/rag.py`(에러 변환) → `rag.py`(엔진).
- **POST 엔드포인트:** 질문 하나지만 향후 top_k·사용자 메타데이터 등 복잡한 요청에 대비.
- **출처 반환:** `RunnableParallel`로 검색을 1회만 수행해 답변 생성과 출처 추출이 같은 결과를 공유.

## 느낀 점

API 무료 한도 안에서 작업하면서 호출 에러를 자주 마주쳤다. 처음엔 API 임베딩 모델과 벡터 DB 클라우드로 구현하려 했지만 이번 프로젝트 규모에는 맞지 않았다. 어느 수준의 기술을 쓸지 직접 조사하고 결정하는 과정에서, 로컬 모델로 전환하며 선택의 근거를 깊이 생각해볼 수 있었다.

검색 성능은 모델보다 데이터 구조가 더 중요하다는 것도 느꼈다. Q3 문제를 해결하면서 특히 체감했고, 어느 문서를 넣느냐에 따라 답변이 크게 달라지는 걸 보며 데이터와 전처리의 중요성을 다시 확인했다.

## 보완하고 싶은 점

- reranker 도입을 통해 검색 성능을 개선하고 싶다.
- RAGAS 지표(faithfulness, context_precision 등)를 추가해 지금 세 지표로 못 잡는 품질 측면을 보완하고 싶다.
- 더 다양한 문서로 테스트해보고 도메인 확장을 통해 프로젝트 방향을 확실하게 가져가고 싶다.
- LangGraph를 도입해 다단계 검색과 추론이 가능하게끔 Agentic한 RAG를 구현하고자 한다.
